# Global View ECS site stack

Use this root for the twelve-camera YOLO11s pilot. It provisions one ECS cluster per site and one Fargate service per cloud camera. Each camera gets an outbound-only security group, a startup role for its own secret, a runtime role for its own encrypted SQS queue, and a log group. A service initially has zero tasks. Set `enabled = true` after staging its private configuration and publishing the camera policy.

## Deploy the development release

1. Use a private VPC with routes to the site's approved RTSP endpoint and HTTPS analytics gateway. Supply the existing VPC and task subnet IDs. To pull images, load secrets, emit logs, and use queues, the tasks need HTTPS access to ECR, S3, Secrets Manager, CloudWatch Logs, and SQS. Use private endpoints and DNS or approved NAT egress. For endpoint-only deployments, allow the interface endpoints' IPs or subnet CIDRs, their security groups' inbound HTTPS, and the S3 gateway endpoint prefix list. Routes for different sites must resolve to the intended camera and gateway, including when customer subnets overlap. [Fargate networking](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-networking.html) · [ECR endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html)
2. Authenticate Docker to an existing private ECR repository in the site's Region and set `PROXIGO_ECR_IMAGE` to its repository URI. Place an approved `yolo11s.onnx` export in the model directory and set `PROXIGO_CCTV_MODEL_SHA256` to its verified digest. Use a self-contained FP32 COCO detection export with batch 1, 640 × 640 input, static shapes and embedded NMS disabled. The build and worker verify the digest. Record the image digest and use it for both evaluation and deployment. [YOLO11](https://docs.ultralytics.com/models/yolo11/) · [ONNX export](https://docs.ultralytics.com/integrations/onnx/) · [Ultralytics licensing](https://www.ultralytics.com/license)

   ```bash
   docker buildx build --platform linux/amd64 --target ecs \
     --build-context cctvmodels=/path/to/approved/models \
     --build-arg CCTV_GROUND_MODEL_SHA256="$PROXIGO_CCTV_MODEL_SHA256" \
     -f docker/cctv-analytics/Dockerfile \
     --tag "$PROXIGO_ECR_IMAGE:pilot" --push .
   ```

3. Create one Secrets Manager secret per camera using the AWS-managed Secrets Manager key. Its value is JSON with `source`, `gateway`, and `gatewayToken`. Use the same enrolled cloud token at the site gateway. Optional keys are `caBundle` with the private CA PEM, `width`, `height`, `fps`, `inferenceFps`, and `inferenceThreads`. Default dimensions are 640 × 360 with a 4 fps decode and inference target. Match the source aspect ratio. YOLO11s starts with two inference threads. For higher inference rates, set `inferenceFps` explicitly and set `fps` at least as high. The task writes configuration on its private ephemeral volume. Pass only the secret ARN to Terraform. [ECS secret injection](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html)
4. Copy `pilot.tfvars.example` to `pilot.tfvars` and supply the real values. The camera map keys must match the published camera IDs. Use isolated Terraform state per site. Configure an existing encrypted, versioned S3 state bucket with a distinct key and the lockfile when sharing changes across a team. [Terraform S3 state](https://developer.hashicorp.com/terraform/language/backend/s3)

   ```bash
   terraform -chdir=infra/ecs-cctv init
   terraform -chdir=infra/ecs-cctv fmt -check -recursive
   terraform -chdir=infra/ecs-cctv validate
   terraform -chdir=infra/ecs-cctv test
   terraform -chdir=infra/ecs-cctv plan -var-file=pilot.tfvars -out=pilot.tfplan
   ```

5. Apply the approved plan. Use the cluster, task definition, and security group from the Terraform outputs for a one-off ECS task. Use the same private subnets, public IP disabled, and override the worker command with `["--check-connection"]`. Publish the camera's cloud policy in Observe mode before the check. The task verifies the site identity, RTSP stream, and telemetry path. Then enable the service in Terraform and use Posture to confirm the actual worker heartbeat. Deploy a fresh task after rotating credentials. [Cloud commissioning](../../docs/cctv-cloud-pilot.md)

## Commission twelve cameras

The example starts with 2 vCPU and 4 GiB per camera. Twelve parallel workers reserve 24 vCPU and 48 GiB. Allow 12 free task IPs across the private subnets plus headroom for other workloads. Check the applied regional Fargate On-Demand vCPU quota. Enable two cameras, then six, then twelve in Observe mode. Check that every camera reports the intended model and stays near 4 inference fps through sustained activity. Measure event delay and dropped or missed detections at each stage. Also run an authorized camera reconnect and check that the other workers keep reporting. [Fargate quotas](https://docs.aws.amazon.com/general/latest/gr/ecs-service.html) · [Task networking](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-networking.html)

A 4 fps analytics target sets sampling after decode. It does not reduce the camera-to-cloud bit rate. Use the recorder's approved analytics substream and measure its bit rate and encoder session limits. For example, twelve streams at 1 Mbps need about 12 Mbps of site uplink before protocol overhead. [Live capacity test](../../docs/cctv-analytics.md#twelve-camera-load-test)

## Growth and recovery

- Use `worker_image_digest` for a per-camera canary from the same ECR repository. Optional camera `cpu` and `memory` override `worker_capacity`. Qualify new images in Observe mode and size workers from measured live inference and alert delay. The explicit build profiles `CCTV_GROUND_MODEL=yolox_nano` and `CCTV_GROUND_MODEL=yolox_s` support existing YOLOX deployments. [YOLOX ONNX models](https://github.com/Megvii-BaseDetection/YOLOX/tree/main/demo/ONNXRuntime)
- To evaluate YOLO11l on a difficult camera, put an approved `yolo11l.onnx` export in the build context and add `--build-arg CCTV_GROUND_MODEL=yolo11l`. Pass its SHA-256 to `CCTV_GROUND_MODEL_SHA256` and pin the resulting image digest for that camera. Check the 4 fps target and alert timing on the intended compute before enabling alerts. [YOLO11 model profiles](https://docs.ultralytics.com/models/yolo11/) · [Site replay comparison](../../docs/cctv-analytics.md#yolo11s-and-yolo11l-comparison)
- To evaluate the near-infrared person model on one camera, put the approved single-class export in the named build context as `yolo11-person.onnx` alongside the general YOLO11 export. Build with `--target ecs-person` and `--build-arg CCTV_PERSON_MODEL_SHA256=<approved-digest>` in addition to the general model's digest. Pin the resulting image digest for the camera and set `"personModel": true` in its secret. Cameras with active person and vehicle rules use both models, so measure inference rate with the published rules. [Near-infrared evaluation](../../docs/cctv-analytics.md#near-infrared-person-model)
- For a camera that switches from color to monochrome infrared, add `"personModelMode": "monochrome"` to that secret. Validate both modes and the transition in Observe mode using the camera's actual substream. [Day and night replay](../../docs/cctv-analytics.md#cameras-that-switch-from-color-to-infrared)
- If short RTSP delivery bursts coincide with missed events, test `"liveFrameBufferMs": 350` for that camera. The ground worker can process recent decoded frames in order while the deadline and three-frame storage limit keep the backlog bounded. Compare alert recall and delivery time with the camera's actual stream. [RTSP burst handling](../../docs/cctv-analytics.md#retain-recent-samples-during-rtsp-bursts)
- For a fixed area that needs extra visual detail, set `detailRegion` in the camera's private worker JSON using normalized left, top, right, bottom coordinates. Use a stream and decode size that preserve the detail. The second YOLO11 pass contributes person detections by default. Set `detailObjects` to `["vehicle"]` or `["person", "vehicle"]` to include vehicles. Verify inference rate and alert behavior with the rest of the site's cameras running. [Distant doorway and roadway evidence](../../docs/cctv-analytics.md#distant-doorways-and-vehicles)
- Set `"detailFromRules": true` in a YOLO11 camera secret to derive a person crop from its published CCTV image rules. For separated zones, add `"detailRegionLimit": 2` to use up to two crops when the combined crop is too large. Choose either rule-derived detail or `detailRegion`. Posture shows the resulting crop fingerprint. [Detail from published person rules](../../docs/cctv-analytics.md#detail-from-published-person-rules)
- Set `"vehicleStopConfirmationBoost": true` in a YOLO11 camera secret to double the sampling rate during an active movement-confirmation stop. Set `fps` to at least twice `inferenceFps`, such as 8 fps decode and 4 fps regular inference. Enable **Require movement before the stop** on the camera rule. [Vehicle stop confirmation](../../docs/cctv-analytics.md#confirm-movement-before-a-vehicle-stop)
- For a sideways or inverted view, set `rotationDegrees` in that camera's private worker JSON to the clockwise angle that aligns its subjects. Keep the decode size, rules, and regions in the source stream coordinates. Confirm the orientation and live detections for that camera in Observe mode. [Rotation replay](../../docs/cctv-analytics.md#time-in-zone-replay)
- For a wider model input, build with the chosen static export named `yolo11s.onnx` or `yolo11l.onnx` and pin its digest. For a dedicated person crop, place the approved `yolo11s-pose.onnx` or `yolo11l-pose.onnx` in the named model build context. Use `--target ecs-pose`, `--build-arg CCTV_DETAIL_POSE_MODEL=yolo11s-pose` or `yolo11l-pose`, and `--build-arg CCTV_DETAIL_POSE_SHA256=<digest>`. The pose build target defaults to `yolo11l-pose`. Pin that image for the camera and set `"detailPose": true` in its secret along with a person `detailRegion` or `"detailFromRules": true`. [Wider inputs and pose replay](../../docs/cctv-analytics.md#wider-input-and-shadowed-doorways)
- With `"detailPose": true`, add `"detailPoseFallback": true` to use the ordinary person crop first and run pose when a covered entry or dwell zone has no qualifying person. Budget for three passes on samples from an empty zone. [Pose fallback](../../docs/cctv-analytics.md#try-pose-when-the-person-zone-has-no-qualifying-box)
- To evaluate continuity for reported YOLO11 person entries, set `"personTrackSupport": true` in the camera secret. Review duplicates and distinct entries in Observe mode over continuous recordings. [Continuous doorway replay](../../docs/cctv-analytics.md#continuous-doorway-replay)
- For a camera with pedestrian track swaps at a tripwire, test `"personMotionAssociation": true` and compare the camera's reviewed event counts in Observe mode. [Crowded walkway crossings](../../docs/cctv-analytics.md#crowded-walkway-crossings)
- To preserve a confirmed pedestrian approach across a brief detection gap, set `"personTripwireRecovery": true` in the camera secret. Review the result in Observe mode with the intended camera stream. [Tripwire gap recovery](../../docs/cctv-analytics.md#recover-a-crossing-across-a-brief-detection-gap)
- To distinguish nearby pedestrian tracks using a color cue, set `"personColorAssociation": true` in the camera secret. [Color-based association](../../docs/cctv-analytics.md#use-color-to-distinguish-nearby-pedestrian-tracks)
- Add cameras by adding map entries. Increase the CPU and memory of an individual worker after measuring it. With one service per camera, new deployments use a stop-before-start policy and can briefly interrupt inference. Add exclusive worker ownership before introducing overlapping releases or a scheduler that assigns the same camera across pools. [ECS deployment parameters](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-ecs.html)
- Add sites by repeating the stack with separate state, secrets, routes and camera roles. Depending on the customer's requirements, deploy it in a dedicated VPC or AWS account. For higher stream density or GPU models, add ECS on EC2 or ECS Managed Instances and adapt task storage to that compute option. Keep per-camera isolation and the site gateway API. [ECS compute options](https://aws.amazon.com/ecs/pricing/) · [ECS bind mounts](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mounts.html)
- The cloud worker sends detection metadata to its private SQS queue and deletes it after the gateway accepts or rejects the observation. Stable event IDs let the gateway deduplicate repeated delivery. SQS-acknowledged detections survive task replacement within the four-day retention window. If SQS is temporarily unavailable, the worker stages events in its task-local SQLite database and retries. That staging data exists only for the life of the task. Drain the queue before retiring a service or switching a camera to on-premises. [SQS delivery semantics](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues.html)
- Keep site recordings on the existing recorder. If a customer approves cloud archive, use S3 with lifecycle rules and AWS Batch jobs with their own compute limits for replay and backfills. The live worker processes the current approved stream. In on-premises mode the local outbox supplies the retry path. [S3 lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html) · [AWS Batch compute environments](https://docs.aws.amazon.com/batch/latest/userguide/compute_environments.html)

The first deployment test should run two sites in Observe mode, replace one task while its site is unreachable, then confirm that its queued detections replay into the correct site once service resumes. Measure real-time inference rate and alert delay on each site before promoting rules.
